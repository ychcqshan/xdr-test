# XDR 平台用户管理深度设计文档

## 一、 设计背景
在 XDR 平台中，“用户”存在两个完全不同的业务语境：
1. **资产用户 (Asset User)**：指运行 Agent 的终端设备的主要使用人。其信息属于“资产属性”，用于威胁追溯和责任判定。
2. **后台用户 (System User / User Info)**：指登录 XDR 管理控制台进行运维、分析、审计的人员。其信息属于“权限实体”，用于系统准入和操作审计。

本设计旨在从数据库层面和逻辑层面对两者进行物理隔离，同时统一其组织机构数据模型，以支持复杂的企业层级管理。

---

## 二、 组织机构模型 (Organization Model)
为了适应集团化部署，本系统采用扁平化的四级单位结构辅以灵活的部门字段：

- **Level 1 (集团公司)**: 顶级节点。
- **Level 2 (二级单位)**: 省、直属机构等。
- **Level 3 (三级单位)**: 市、分支构等。
- **Level 4 (四级单位)**: 县、科室、变电站等。
- **部门 (Department)**: 具体业务团队。
- **岗位 (Post)**: 用户在部门中的职责描述。

## 三、 数据库设计

### 3.1 资产用户表 (`asset_user`)
**数据库**: `xdr_asset`  
**用途**: 存储由 Agent 采集或人工绑定的终端使用人信息。

| 字段名 | 类型 | 描述 | 约束 |
| :--- | :--- | :--- | :--- |
| `id` | VARCHAR(36) | 主键 | PK |
| `agent_id` | VARCHAR(50) | 关联 Agent | UNIQUE, INDEX |
| `username` | VARCHAR(50) | 姓名/使用人 | NOT NULL |
| `phone` | VARCHAR(20) | 手机号 | - |
| `email` | VARCHAR(100) | 邮箱 | - |
| `unit_level1` | VARCHAR(100) | 一级单位 (集团公司) | INDEX |
| `unit_level2` | VARCHAR(100) | 二级单位 | INDEX |
| `unit_level3` | VARCHAR(100) | 三级单位 | - |
| `unit_level4` | VARCHAR(100) | 四级单位 | - |
| `department` | VARCHAR(100) | 部门 | - |
| `post` | VARCHAR(50) | 岗位 | - |
| `created_at` | DATETIME | 创建时间 | - |
| `updated_at` | DATETIME | 更新时间 | - |

### 3.2 后台用户表 (`user_info`)
**数据库**: `xdr_auth`  
**用途**: 存储具备后台登录权限的运维管理人员信息。

| 字段名 | 类型 | 描述 | 约束 |
| :--- | :--- | :--- | :--- |
| `id` | VARCHAR(36) | 主键 | PK |
| `login_name` | VARCHAR(50) | 登录账号 | UNIQUE, NOT NULL |
| `password` | VARCHAR(255) | 加密密码 | NOT NULL |
| `real_name` | VARCHAR(50) | 真实姓名 | NOT NULL |
| `role` | VARCHAR(20) | 角色 (ADMIN/OPERATOR/AUDITOR) | NOT NULL |
| `status` | INT | 状态 (1-启用, 0-禁用) | DEFAULT 1 |
| `unit_level1` | VARCHAR(100) | 集团公司 (一级) | - |
| `unit_level2` | VARCHAR(100) | 二级单位 | - |
| `unit_level3` | VARCHAR(100) | 三级单位 | - |
| `unit_level4` | VARCHAR(100) | 四级单位 | - |
| `department` | VARCHAR(100) | 部门 | - |
| `post` | VARCHAR(50) | 岗位 | - |
| `phone` | VARCHAR(20) | 手机号 | - |
| `email` | VARCHAR(100) | 邮箱 | - |
| `last_login` | DATETIME | 最后登录时间 | - |

## 四、 核心逻辑流

### 4.1 资产-用户联动逻辑
当 Agent 上报用户信息时：
1. `AssetService` 接收数据。
2. 写入/更新 `xdr_asset.asset_user` 表。
3. 同步关键字段（`unit_level1`, `username`）至 `xdr_asset.asset` 表的冗余字段中，以保证列表查询性能。

### 4.2 组织架构一致性校验
系统管理模块应维护一套全局的组织架构枚举或字典表（后期演进），现阶段通过字符串匹配确保 `asset_user` 与 `user_info` 在筛选统计时能够归并至同一单位。

## 五、 接口设计

### 5.1 资产用户上报
- **URL**: `POST /api/v1/assets/{agentId}/asset-user`
- **Body**:
```json
{
  "username": "张三",
  "unitLevel1": "XX集团",
  "unitLevel2": "北京分公司",
  "department": "信息部",
  "post": "安全运维岗",
  "phone": "13800000000"
}
```

### 5.2 后台用户管理
- **URL**: `POST /api/v1/auth/users`
- **URL**: `GET /api/v1/auth/users/me` (获取当前登录用户及组织属性)
